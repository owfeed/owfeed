# owfeed

*[English version](README.md)*

Один бинарь. Превращает каталог в подписанный фид для **обеих релизных линий** — apk для
OpenWrt 25.12 и новее, opkg для 24.10 и старее, — чтобы ваши пользователи выполнили три строки
и `apk add` заработал.

Noarch-пакет на все 35 архитектур — собран, подписан, проиндексирован, разложен — ~25 секунд.
Статус-кво: 35 сборок через SDK.

**В первый раз?** [Кукбук](https://owfeed.org/cookbook/ru/) проходит весь путь целиком — собрать
пакет, проверить на живом роутере, подписать, попасть в фид — с файлами, которые можно скопировать.

---

## Установка

```sh
go install owfeed.org/owfeed/cmd/owfeed@latest
```

Либо релизный бинарь, сверенный с аттестацией, которую выпустил собственный workflow GitHub, — а не
с контрольной суммой из того же релиза, которую подменивший бинарь подменил бы заодно:

```sh
gh release download v0.5.1 -R owfeed/owfeed -p 'owfeed-linux-amd64'
gh attestation verify owfeed-linux-amd64 -R owfeed/owfeed \
  --signer-workflow owfeed/owfeed/.github/workflows/release.yml
chmod +x owfeed-linux-amd64 && sudo mv owfeed-linux-amd64 /usr/local/bin/owfeed
```

В GitHub Actions эту проверку делает за вас `owfeed/owfeed/setup@v0.5.1`. Сборки есть под linux и
darwin, amd64 и arm64.

**Что нужно рядом.** Для `build`, `sign`, `index` и `publish` — ничего: apk-тулчейн скачивается из
OpenWrt SDK и проверяется запиненным ключом подписи, ставить нечего. `smoke` требует Docker, потому
что установка на живой образ OpenWrt — весь его смысл. На macOS Docker нужен и для `build`:
apk-tools там не собирается.

## А фид вам вообще нужен?

Скорее всего нет, и об этом сказано до того, как вам что-то продали.

Ключ в `/etc/apk/keys` — trust anchor для **любого имени пакета**, не только вашего. Утёкший ключ
фида позволяет предложить версию `dropbear` постарше и выиграть резолвинг, а отзыва у apk нет: ни
CRL, ни срока годности, ни способа сказать, что ключ мёртв.

**Один пакет, который ставят изредка:** публикуйте подписанные артефакты релиза. `owfeed release`
ровно это и делает — пакеты плюс подписанный манифест — и не просит от пользователей ничего, кроме
проверки подписи. Фид не нужен.

**Несколько пакетов, или нужен рабочий `apk upgrade`:** это умеет только фид, потому что apk
обновляет из индекса и больше ниоткуда. Тогда читайте дальше.

## Почему не `openwrt/gh-action-sdk`?

Потому что он компилятор, а это публикатор. Они делают разные половины, и большинству
третьесторонних пакетов нужна только вторая.

| | `gh-action-sdk` | `owfeed` |
|---|---|---|
| что делает | собирает пакет из исходников, в SDK | пакует уже собранный каталог |
| noarch на 35 архитектур | 35 сборок SDK | одна, ~25 секунд |
| индекс | — | подписанный, apk и opkg сразу |
| подпись | `PRIVATE_KEY` пишется в `$TOPDIR` | ключ вообще не попадает в сборочный job |
| публикация | — | GitHub Pages, через гейт |
| доказательство, что ставится | — | `smoke`, на живом образе OpenWrt, с провалом, если apk просит `--allow-untrusted` |
| доказательство, что живой фид работает | — | `verify`, по задокументированному URL |
| релизные линии | одна за запуск | apk и opkg из одного конфига, каждая подписана схемой, которую проверяет её менеджер |
| конфиг | входы workflow | `owfeed.yml` с [опубликованной схемой](schema/v1.json), сгенерированной из кода |

Если ваш пакет — компилируемый C, вам нужен SDK, и `owfeed` спокойно упакует то, что он выдал. Если
это тема LuCI, приложение LuCI, скрипт или статический бинарь — SDK это 35 сборок ради того, что
компилировать не требовалось.

## Как это устроено

**Фид — это каталог файлов, отдаваемый по HTTPS.** Ни серверного софта, ни базы данных. Вы делаете
каталог; отдать его может что угодно, умеющее статику.

```
feed/
  myfeed.pem                            ваш ПУБЛИЧНЫЙ ключ
  releases/25.12/x86_64/
    packages.adb                        подписанный индекс (бинарный)
    index.json                          то же самое в JSON
    sha256sums
    netwatch-1.4.0-r1.apk                  сами пакеты, плоско рядом с индексом
    luci-app-netwatch-1.4.0-r1.apk
  releases/25.12/aarch64_cortex-a53/    те же файлы ещё раз
  …                                     35 каталогов, по одному на архитектуру
```

**На роутере происходит четыре вещи:**

1. Пользователь кладёт ваш `.pem` в `/etc/apk/keys/`. Теперь роутер доверяет вашей подписи.
2. Пишет одну строку в `/etc/apk/repositories.d/<feed>.list` — прямой URL до `packages.adb`.
3. `apk update` скачивает индекс и проверяет его вашим ключом.
4. `apk add netwatch` находит в индексе `netwatch 1.4.0-r1`, **выводит имя файла из имени и версии**,
   качает `netwatch-1.4.0-r1.apk` из того же каталога, сверяет с хешем, записанным в индексе, и ставит.

**Куда именно ставится?** Payload пакета — это и есть кусок корневой файловой системы. Что вы
положили в `staging/netwatch/etc/config/netwatch`, приедет в `/etc/config/netwatch`.

**Почему 35 копий одного файла?** В режиме `ndx` роутер читает ровно один индекс — свой, по
архитектуре. Noarch-пакет обязан лежать во всех. Копии побайтово одинаковы.

Стадии ложатся на это один в один:

| | |
|---|---|
| `build` | подготовленный каталог → файлы `.apk` |
| `sign` | подпись в каждый `.apk` |
| `index` | разложить по 35 каталогам, в каждый написать подписанный `packages.adb` |
| `publish` | проверить всё и отдать каталог тому, кто заливает |

---

**Две релиз-линии, два пакетных менеджера.** 25.12 и новее — apk; 24.10 и старее — opkg, и они не
совпадают почти ни в чём: другой индекс, другая схема подписи, другое слово для
«архитектурно-независимый». owfeed публикует любую из линий или обе из одного конфига и держит обе
под одними проверками.

| | 25.12+ (apk) | 24.10 и старее (opkg) |
|---|---|---|
| индекс | бинарный `packages.adb` | текстовый `Packages` + `Packages.gz` |
| что покрыто подписью | сам индекс | **несжатый** `Packages` |
| подпись | EC prime256v1 | usign / ed25519 |
| строка репозитория | URL **файла** индекса | URL **каталога** |
| ключ ставится как | `/etc/apk/keys/<любое имя>.pem` | `/etc/opkg/keys/<id ключа>` |
| подпись каждого пакета | есть | нет — доверие держится на индексе |
| «любая архитектура» | `noarch` | `all` |

Фид, обслуживающий обе линии, подписывается двумя ключами. Это не выбор: каждый менеджер проверяет
только свою схему.

## Хочу опубликовать фид

```sh
owfeed init --url https://feed.example.org
owfeed keygen -o ~/keys/myfeed.pem      # вне репозитория. Опубликованный ключ не отозвать.
export OWFEED_SIGN_KEY="$(cat ~/keys/myfeed.pem)"

# правим owfeed.yml: `files:` смотрит на каталог, разложенный так, как он должен установиться

owfeed lock --update                    # выводит список архитектур; закоммитьте его
owfeed build && owfeed sign && owfeed index
owfeed doctor
```

`out/` — это и есть фид. Заливайте.

## Хочу выпустить новую версию

Поднимите `version:` в `owfeed.yml`, дальше:

```sh
owfeed build && owfeed sign && owfeed index && owfeed doctor
```

## Хочу добавить пакет

Ещё одна запись в `packages:`. Те же четыре команды.

## Хочу пакет только на одной линии

```yaml
releases:
  - line: "25.12"
    default: true
    format: apk
  - line: "24.10"
    format: ipk

packages:
  - name: luci-app-mine        # нет `releases:` — едет в обе
    ...
  - name: luci-app-mine-new
    releases: ["25.12"]        # только 25.12
    ...
```

Один `owfeed build` собирает все линии, каждую в её формате. Один `owfeed index` публикует все.

## Хочу выдать пользователям инструкцию

```sh
owfeed install-snippet             # markdown, вставить в README
owfeed install-snippet --format sh # только команды
```

Не пишите свою. `doctor` сверяет ваш README с этим выводом — фид, у которого задокументированный
URL отдаёт 404, прямо сейчас живёт в природе.

## Хочу это в CI

Всё целиком, в правильной форме, — один job:

```yaml
jobs:
  publish:
    permissions:                 # вызванный workflow может их только сузить,
      contents: read             # поэтому права выдаёт вызывающий
      pages: write
      id-token: write
      actions: read
    uses: owfeed/owfeed/.github/workflows/feed.yml@v0.5.1
    with:
      owfeed-version: v0.5.1
      smoke-releases: "25.12 24.10"
    secrets:
      sign-key: ${{ secrets.OWFEED_SIGN_KEY }}
      usign-key: ${{ secrets.OWFEED_USIGN_KEY }}   # только если обслуживаете 24.10
```

Он разводит сборку и публикацию, чтобы ключ подписи не оказался в job, который выполняет ваши
сборочные скрипты, гейтит выгрузку через `owfeed publish` и ставит пакеты на живой образ OpenWrt
до того, как что-либо уедет. `pre-build:` и `post-index:` принимают шелл, если ваш фид что-то
докачивает или проверяет сам.

Ключи подписи должны быть секретами репозитория или организации, не environment: у вызывающего
job нет environment, поэтому прочитать environment-секрет и передать дальше он не может.
`environment:` на publish-job при этом остаётся тем, что ставит прогон за ревьюера.

Если шаги нужны свои — берите инструмент, оставьте форму:

```yaml
- uses: owfeed/owfeed/setup@v0.5.1
  with: { version: v0.5.1 }
- run: owfeed --frozen-lock build && owfeed sign && owfeed index
  env:
    OWFEED_SIGN_KEY: ${{ secrets.OWFEED_SIGN_KEY }}
- run: owfeed publish            # откажется публиковать сломанное дерево. Флага обхода нет.
- uses: actions/upload-pages-artifact@v3
  with: { path: out }
- uses: actions/deploy-pages@v4
```

Вынесите `publish` в отдельный job с `environment:`, чтобы PR из форка не дотянулся до ключа.

`setup` скачивает один бинарь и сверяет его с build-аттестацией GitHub до запуска — не с файлом
контрольных сумм из того же релиза, который тот, кто подменил бинарь, подменил бы заодно.

## В апстриме появилась новая архитектура

```sh
owfeed lock --update    # печатает диф; закоммитьте
```

`--frozen-lock` будет валить сборку, пока не сделаете. То, что покрывает ваш фид, не должно
меняться без вашего ведома.

## Хочу убедиться, что оно ставится

```sh
owfeed smoke           # ставит собранный фид на живой образ OpenWrt
```

`doctor` доказывает, что дерево согласовано. Это доказывает, что роутер его принимает — по вашей же
опубликованной инструкции, с падением, если apk попросит `--allow-untrusted`. Это разные утверждения.

**Это не [owlab](https://github.com/owfeed/owlab) и его не использует.** owlab того же автора — это
цикл разработки: несколько релизов рядом друг с другом столько, сколько идёт работа, исходники
синкаются внутрь, LuCI открыт в браузере. `owfeed smoke` — одна проверка перед публикацией: одна
архитектура, одна установка, один ответ, и всё исчезло. Они независимы намеренно: зависимость
инструмента публикации от инструмента разработки означала бы, что ответ на «поставится ли фид»
зависит от того, правильно ли установлен owlab, — ради переиспользования кода вызова Docker.
Разрабатывайте в owlab, если хотите; публиковать всё равно owfeed.

Композиция при этом есть — через формат файлов, а не через зависимость: `owlab build` пишет
`dist/<arch>/`, и каждая стадия здесь этот каталог читает. Где проходит граница, какие инварианты
по обе её стороны и какие контракты её пересекают — [ECOSYSTEM.md](docs/ECOSYSTEM.md).

## Хочу проверить, что уже опубликовано

```sh
owfeed verify out      # забирает опубликованный фид по задокументированному URL
```

Ловит редирект, по которому apk не пойдёт; пакет, который живой индекс называет, а его нет или он
другого размера; и — если дать дерево, которое его заменит, — версию, перепубликованную с другим
содержимым.

## Что-то сломалось

```sh
owfeed doctor          # нумерованные находки: почему это важно и что делать
```

## Что вас укусит

owfeed отказывается от каждого из этих пунктов. На каждом уже погорел живой мейнтейнер.

| | |
|---|---|
| `arch: all` | apk считает такой пакет неустанавливаемым. Нужно `noarch`. |
| Ключ PKCS#8 | `openssl genpkey -algorithm EC` пишет не тот PEM. Работает только SEC1. |
| `1.0~beta` | после `~` apk читает commit-хеш, только hex. Пишите `_beta1`. |
| Фид за редиректом | apk не ходит по 30x ([openwrt#17180](https://github.com/openwrt/openwrt/issues/17180)). |
| Нет записи в `keep.d` | `/etc/apk/keys/*.pem` **не** переживают sysupgrade. Причина №1 сообщений `UNTRUSTED signature` после апгрейда. |
| Индекс раньше подписи | подпись дописывает байты, и индекс перестаёт совпадать с файлом. |
| `/etc/config/foo` не в `conffiles:` | sysupgrade молча заменит настройки пользователя вашими дефолтами при каждом апгрейде. |
| `.po` в payload | LuCI читает скомпилированные `.lmo`. Укажите `i18n.from:`, owfeed их соберёт. |
| README разошёлся с реальностью | уже живёт в крупном фиде. |
| Пакет, который сборка потеряла | отсутствие невидимо любой проверке, читающей дерево, поэтому owfeed сверяет дерево с конфигом. |

## Чего owfeed не притворяется

- **У apk нет отзыва.** Ни CRL, ни срока годности, ни сигнала «ключ мёртв». owfeed делает ротацию
  дешёвой; он не утверждает, что отзыв существует.
- **Ваш ключ — trust anchor для любого имени пакета**, не только вашего — см.
  [А фид вам вообще нужен?](#а-фид-вам-вообще-нужен), который стоит первым разделом не случайно.
- **Attended Sysupgrade не перенесёт ваши пакеты.** `owut` не передаёт кастомные репозитории вообще,
  а `repository_allow_list` на сервере ASU по умолчанию пуст, и пустой запрещает всё.
- **`build` пакует каталог, а не собирает его.** CSS должен быть уже собран. Каталоги `.po` owfeed
  компилирует сам — LuCI читает `.lmo` и `.po` игнорирует, эта дыра молчаливая и её стоит закрыть, —
  но вашу сборку он за вас не запустит и исходники паковать откажется.

## Чего ещё нет

Объявлены в схеме конфига, чтобы попытка их написать давала внятную ошибку, а не тихо
ничего не делала, но **не реализованы**: `retention:`, `overrides:`,
`build.changed-only`, `version-from: git-describe`, а также цели публикации `s3` и `rsync`. Работает только `github-pages`.

Кроме того, нет: SBOM, команд ротации ключа и переиспользования уже опубликованного пакета
вместо переподписи без изменений.

**Сборок через SDK в этом списке нет и не будет.** owfeed пакует, но не компилирует. Собирайте
[owlab](https://github.com/owfeed/owlab), `openwrt/gh-action-sdk` или своим вызовом SDK и
оставьте результат в `dist/<arch>/` — каждая стадия здесь читает этот каталог и не спрашивает, чем
сделаны байты. Где проходит граница и почему именно там — [контракт артефакта](docs/artifact-contract.md)
и [ECOSYSTEM.md](docs/ECOSYSTEM.md).

## Фид, собранный этим

[owfeed/owfeed-packages](https://github.com/owfeed/owfeed-packages) — живой фид: тема LuCI и
статический Go-бинарь на 20 архитектур. Пулл-реквесты собирают, подписывают, индексируют и проверяют
всё целиком на одноразовом ключе, так что форк к ключу фида не приближается.


## Чужой CI, мой фид

Фид, несущий чужие пакеты, не может отдать им свой ключ подписи — и не обязан. Авторы собирают и
подписывают в своём CI и публикуют подписанный релиз; фид забирает и проверяет подпись автора против
запиненного ключа.

Что фид подписывает дальше — его выбор. По умолчанию он подписывает и каждый пакет, а блоки подписей
в apk складываются, поэтому файл, который ставит роутер, несёт **обе**. Фид, который не хочет класть
свою подпись внутрь чужого артефакта, ставит `signing.sign-packages: false` и подписывает только
индекс — а роутер и так берёт доверие именно оттуда. Установка, обновление и удаление по имени
работают ровно так же; перестают работать `apk add ./file.apk` и загрузка файла через LuCI, которым
и для собственных пакетов OpenWrt нужен `--allow-untrusted`.

```sh
owfeed sign                       # в CI автора, ключом автора
owfeed doctor --require-origin    # каждый пакет называет свой репозиторий
```

### Если вы автор

У вашего репозитория есть ipk-линия, а индекс он не собирает: индекс подписывает своим ключом фид на
дальнем конце. Вы публикуете релиз и подписанную опись того, что в него входит.

```sh
owfeed --frozen-lock build
owfeed release --repo "$GITHUB_REPOSITORY" --tag "$GITHUB_REF_NAME"
```

Ещё до всего этого `owfeed plan` говорит, что даст сборка — версию, архитектуры и путь каждого
файла, — офлайн и не собирая. У `--json` есть версия схемы, так что следующий job читает его вместо
того, чтобы шарить по `dist/`. Раньше всего он отвечает при `version-from: tag`: версия берётся из
собираемого тега (`tag:v` срезает `v`), а не из файла, который сборочный скрипт ещё не написал.

```sh
owfeed plan
```

На пулл-реквесте тега нет, и ключа быть не должно: секрет подписи в job'е, который выполняет код
форка, — это секрет, на который форк может навести работу. Одна команда покрывает всё, что
проверяется без ключа:

```sh
owfeed check                      # build, sign, index, doctor --require-origin
```

Она создаёт по одноразовому ключу каждого вида, пользуется ими на время запуска и выбрасывает. Она
отвечает, собирается ли пакет, подписывается ли и индексируется ли и переживает ли дерево `doctor` —
а ни одно из этого не зависит от того, чьим ключом подписано. **Блок `signing:` ей не нужен**, и это
вторая причина, по которой она существует: репозитории, публикующие ассеты релиза и никакого фида,
объявляли его только потому, что `index` без usign-ключа не запускается.

`release` пишет `manifest.txt` — что входит в релиз, размер и хеш каждого файла — и подписывает его
usign-ключом: это схема, которую OpenWrt уже везёт в base-files, поэтому роутер проверяет её ничего
не устанавливая. Манифест несёт имя репозитория, и читатели его проверяют: подпись доказывает, кто
что написал, но никогда — о чём это; без этой строки манифест, взятый из другого вашего релиза,
проверился бы как этот.

Ассеты релиза плоские, а в имени apk архитектуры нет — в фиде архитектура **и есть** каталог. Пакет
на двадцать архитектур дал бы двадцать файлов с одним именем, поэтому `release` дописывает
архитектуру там, где имена сталкиваются, и только там: noarch-пакет сохраняет имя, по которому его
ищет установщик, уже стоящий на роутере.

[CONTRIBUTING фида](https://github.com/owfeed/owfeed-packages/blob/main/CONTRIBUTING_ru.md)
разбирает обе стороны.
