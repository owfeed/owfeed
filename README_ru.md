# owfeed

*[English version](README.md)*

owfeed превращает каталог в подписанный фид пакетов для OpenWrt. Один бинарь покрывает обе релизные
линии: apk для 25.12 и новее, opkg для 24.10 и старее.

- **Вашим пользователям:** три команды, и `apk add` работает.
- **Вам:** noarch-пакет на все 35 архитектур собран, подписан и проиндексирован примерно за 25 секунд.
  Обычный путь — 35 сборок через SDK.
- **В первый раз?** [Кукбук](https://owfeed.org/cookbook/ru/) проходит весь путь с файлами, которые
  можно скопировать.

## Быстрый старт

1. Установите owfeed (см. [Установка](#установка)).
2. Создайте конфиг и ключ. Храните ключ вне репозитория: опубликованный ключ не отозвать.

   ```sh
   owfeed init --url https://feed.example.org
   owfeed keygen -o ~/keys/myfeed.pem
   export OWFEED_SIGN_KEY="$(cat ~/keys/myfeed.pem)"
   ```

3. Отредактируйте запись пакета, которую `init` записал в `owfeed.yml`. `files:` — каталог,
   разложенный так, как он должен установиться: `<files>/etc/config/netwatch` попадает в
   `/etc/config/netwatch`. owfeed упаковывает каталог как есть и ничего не компилирует, поэтому
   сначала соберите CSS или бинарь.

   ```yaml
   packages:
     - name: luci-app-example
       build: mkpkg
       arch: noarch          # never "all": apk rejects it as uninstallable
       version: 1.0.0-r1
       files: ./dist/root
       description: "One line. LuCI truncates past 512 bytes."
       depends: [luci-base]
       conffiles: []         # every /etc/config file the package ships
   ```

   Другие варианты (тема, два пакета, скомпилированный бинарь) — в [примерах](docs/examples_ru.md).
4. Соберите фид:

   ```sh
   owfeed lock --update        # читает архитектуры с downloads.openwrt.org; закоммитьте owfeed.lock
   owfeed build && owfeed sign && owfeed index
   owfeed doctor
   ```

5. Раздайте `out/` по HTTPS. Этот каталог и есть фид, и `index` уже положил в него ваш публичный
   ключ (`out/<feed>.pem`). [CI](#ci) публикует его на GitHub Pages сам.
6. Проверьте на живом образе роутера: `owfeed smoke` (нужен Docker).

## Установка

Скачайте релизный бинарь и сверьте его с build-аттестацией GitHub:

```sh
gh release download v0.5.8 -R owfeed/owfeed -p 'owfeed-linux-amd64'
gh attestation verify owfeed-linux-amd64 -R owfeed/owfeed \
  --signer-workflow owfeed/owfeed/.github/workflows/release.yml
chmod +x owfeed-linux-amd64 && sudo mv owfeed-linux-amd64 /usr/local/bin/owfeed
```

Или соберите через Go: `go install owfeed.org/owfeed/cmd/owfeed@latest`.

- Сборки есть под linux и darwin, amd64 и arm64.
- В GitHub Actions `owfeed/owfeed/setup@v0.5.8` ставит и проверяет бинарь за вас.
- Проверяется аттестация. Контрольная сумма из того же релиза не годится: тот, кто подменил бинарь,
  подменил бы и её.

### Что нужно рядом

| Команда | Нужно |
|---|---|
| `build`, `sign`, `index`, `publish` | ничего; owfeed берёт apk-tools из OpenWrt SDK, проверяет запиненным ключом и пакетов им не компилирует |
| `build` на macOS | Docker: apk-tools там не собирается |
| `smoke` | Docker |
| `smoke -arch` для чего угодно, кроме x86_64, на x86_64-хосте | QEMU: `docker run --privileged --rm tonistiigi/binfmt --install arm64` |

## А фид вам вообще нужен?

Фид подходит не для всякого пакета. Проверьте до начала.

- **Один пакет, который ставят изредка:** публикуйте подписанные артефакты релиза через
  `owfeed release`. Пользователи только проверяют подпись. Фид не нужен.
- **Несколько пакетов, или нужен рабочий `apk upgrade`:** нужен фид. apk обновляет из индекса и
  больше ниоткуда.

Почему это важно: ключу в `/etc/apk/keys` роутер доверяет для **любого имени пакета**, не только
вашего. Утёкший ключ фида позволяет предложить версию `dropbear` постарше и выиграть. Отзыва у apk
нет: ни CRL, ни срока годности, ни способа сказать, что ключ мёртв.

## Как это устроено

Фид — это каталог статических файлов, отдаваемый по HTTPS. Ни серверного софта, ни базы данных.

```
feed/
  myfeed.pem                            ваш ПУБЛИЧНЫЙ ключ
  releases/25.12/x86_64/
    packages.adb                        подписанный индекс (бинарный)
    index.json                          то же самое в JSON
    sha256sums
    netwatch-1.4.0-r1.apk               сами пакеты, плоско рядом с индексом
    luci-app-netwatch-1.4.0-r1.apk
  releases/25.12/aarch64_cortex-a53/    те же файлы ещё раз
  …                                     35 каталогов, по одному на архитектуру
```

На роутере:

1. Пользователь кладёт ваш `.pem` в `/etc/apk/keys/`.
2. Пишет прямой URL до `packages.adb` в `/etc/apk/repositories.d/<feed>.list`.
3. `apk update` скачивает индекс и проверяет его вашим ключом.
4. `apk add netwatch` находит `netwatch 1.4.0-r1`, выводит имя файла из имени и версии,
   качает `netwatch-1.4.0-r1.apk` из того же каталога, сверяет хеш и ставит.

- **Куда ставятся файлы:** payload пакета — это кусок корневой файловой системы.
  `staging/netwatch/etc/config/netwatch` приедет в `/etc/config/netwatch`.
- **Почему 35 копий:** в режиме `ndx` роутер читает только индекс своей архитектуры, поэтому
  noarch-пакет лежит в каждом каталоге. Копии побайтово одинаковы.

| Стадия | Делает |
|---|---|
| `build` | подготовленный каталог → файлы `.apk` |
| `sign` | подпись в каждый `.apk` |
| `index` | раскладывает по 35 каталогам, в каждом пишет подписанный `packages.adb` |
| `publish` | проверяет всё и отдаёт каталог тому, кто заливает |

<details>
<summary>apk и opkg рядом</summary>

25.12 и новее — apk; 24.10 и старее — opkg. Они почти ни в чём не совпадают. owfeed публикует любую
из линий или обе из одного конфига и держит обе под одними проверками.

| | 25.12+ (apk) | 24.10 и старее (opkg) |
|---|---|---|
| индекс | бинарный `packages.adb` | текстовый `Packages` + `Packages.gz` |
| что покрыто подписью | сам индекс | **несжатый** `Packages` |
| подпись | EC prime256v1 | usign / ed25519 |
| строка репозитория | URL **файла** индекса | URL **каталога** |
| ключ ставится как | `/etc/apk/keys/<любое имя>.pem` | `/etc/opkg/keys/<id ключа>` |
| подпись каждого пакета | есть | нет; доверие держится на индексе |
| «любая архитектура» | `noarch` | `all` |

Фид для обеих линий подписывается двумя ключами: каждый менеджер проверяет только свою схему.

</details>

## Пакет только на одной линии

Пакет без `releases:` едет во все линии. Чтобы сузить, перечислите линии:

```yaml
releases:
  - line: "25.12"
    default: true
    format: apk
  - line: "24.10"
    format: ipk

packages:
  - name: luci-app-mine        # нет `releases:` — едет в обе
    ...
  - name: luci-app-mine-new
    releases: ["25.12"]        # только 25.12
    ...
```

Один `owfeed build` собирает все линии, каждую в её формате. Один `owfeed index` публикует все.

## Инструкция для пользователей

```sh
owfeed install-snippet             # markdown, вставить в README
owfeed install-snippet --format sh # только команды
```

Не пишите свою. `doctor` сверяет ваш README с этим выводом: задокументированный URL, который отдаёт
404, прямо сейчас живёт в крупном фиде.

## CI

Всё делает один job:

```yaml
jobs:
  publish:
    permissions:                 # вызванный workflow может их только сузить, но не расширить,
      contents: read             # поэтому права, нужные publish-job, выдаёт вызывающий
      pages: write
      id-token: write
      actions: read
    uses: owfeed/owfeed/.github/workflows/feed.yml@v0.5.8
    secrets: inherit             # publish-job читает ключи из своего environment
    with:
      smoke-releases: "25.12 24.10"
```

1. Сохраните ключи как секреты environment `feed`: `OWFEED_SIGN_KEY`, и `OWFEED_USIGN_KEY`, если
   обслуживаете 24.10. Ключ usign создаёт `owfeed keygen -usign`.
2. Добавьте job выше.
3. Запушьте. Workflow собирает, прогоняет smoke на живом образе OpenWrt, гейтит через
   `owfeed publish` и заливает на GitHub Pages. Полный файл workflow — в
   [кукбуке](https://owfeed.org/cookbook/ru/).

- Ключ подписи не попадает в job, который выполняет ваши сборочные скрипты.
- Environment `feed` объявляет только publish-job, поэтому другие workflow ключи не читают. Секреты
  `sign-key:` и `usign-key:` — запасной вариант для ключей на уровне репозитория.
- Пин — это строка `uses:`. Workflow ставит тот релиз owfeed, которым помечен сам, поэтому бамп от
  dependabot двигает и бинарь. `owfeed-version:` задавайте, только если нужен другой релиз.
- `pre-build:` и `post-index:` принимают шелл, если ваш фид что-то докачивает или проверяет сам.

<details>
<summary>Те же шаги вручную</summary>

```yaml
- uses: owfeed/owfeed/setup@v0.5.8       # ставит owfeed v0.5.8
- run: owfeed --frozen-lock build && owfeed sign && owfeed index
  env:
    OWFEED_SIGN_KEY: ${{ secrets.OWFEED_SIGN_KEY }}
- run: owfeed publish            # откажется публиковать сломанное дерево. Флага обхода нет.
- uses: actions/upload-pages-artifact@v3
  with: { path: out }
- uses: actions/deploy-pages@v4
```

Перед использованием разделите на два job: сборка в одном, `publish` и заливка во втором, с
`environment:`, чтобы PR из форка не дотянулся до ключа. `setup`
сверяет бинарь с build-аттестацией GitHub до запуска.

</details>

## В апстриме появилась новая архитектура

```sh
owfeed lock --update    # печатает диф; закоммитьте
```

`--frozen-lock` валит сборку, пока вы не закоммитите. Покрытие фида не меняется без вашего ведома.

## Убедиться, что оно ставится

```sh
owfeed smoke
```

- `smoke` ставит собранный `out/` на живой образ OpenWrt (`openwrt/rootfs`, Docker скачивает его
  сам). Он идёт по вашей инструкции и падает, если apk просит `--allow-untrusted`.
- `doctor` доказывает, что дерево согласовано; `smoke` — что роутер его принимает.
- По умолчанию — x86_64 и линия, отмеченная `default:` в `owfeed.yml`. `-release 24.10` проверяет
  opkg-линию.
- `smoke -arch aarch64_cortex-a53` ставит на образ этой архитектуры. См. строку про QEMU в
  [Что нужно рядом](#что-нужно-рядом).

<details>
<summary>smoke и owlab</summary>

`smoke` не использует [owlab](https://github.com/owfeed/owlab). owlab — это цикл разработки:
несколько релизов рядом, исходники синкаются внутрь, LuCI открыт в браузере. `smoke` — одна проверка
перед публикацией: одна архитектура, одна установка, один ответ. Если бы инструмент публикации
зависел от инструмента разработки, ответ на «поставится ли фид» зависел бы от того, правильно ли
установлен owlab.

Они стыкуются через формат файлов: `owlab build` пишет `dist/<arch>/`, и каждая стадия здесь читает
этот каталог. Граница и её контракты — в [ECOSYSTEM.md](docs/ECOSYSTEM.md);
[STATUS.md](docs/STATUS.md) говорит, сколько из стороны owfeed уже есть.

</details>

## Проверить, что уже опубликовано

```sh
owfeed verify out      # забирает опубликованный фид по задокументированному URL
```

Ловит редирект, по которому apk не пойдёт, и пакет из индекса, которого нет или он другого размера.
Если дать дерево, которое заменит живое, ловит и версию, перепубликованную с другим содержимым.

## Частые ошибки, которые owfeed отклоняет

owfeed отказывается от каждого из этих пунктов. На каждом уже погорел живой мейнтейнер.

| Ошибка | Что будет |
|---|---|
| `arch: all` | apk считает такой пакет неустанавливаемым. Нужно `noarch`. |
| Ключ PKCS#8 | `openssl genpkey -algorithm EC` пишет не тот PEM. Работает только SEC1. |
| `1.0~beta` | после `~` apk читает commit-хеш, поэтому только hex. Пишите `_beta1`. |
| Фид за редиректом | apk не ходит по 30x ([openwrt#17180](https://github.com/openwrt/openwrt/issues/17180)). |
| Нет записи в `keep.d` | `/etc/apk/keys/*.pem` **не** переживают sysupgrade. Это причина №1 сообщений `UNTRUSTED signature` после апгрейда. |
| Индекс раньше подписи | подпись дописывает байты, и индекс перестаёт совпадать с файлом. |
| `/etc/config/foo` не в `conffiles:` | sysupgrade молча заменяет настройки пользователя вашими дефолтами при каждом апгрейде. |
| `.po` в payload | LuCI читает скомпилированные `.lmo`. Укажите их в `i18n.from:`, и owfeed их скомпилирует. |
| README разошёлся с реальностью | уже живёт в крупном фиде. |
| Пакет, который сборка потеряла | отсутствие невидимо проверкам, читающим дерево, поэтому owfeed сверяет дерево с конфигом. |

## Ограничения

- **У apk нет отзыва.** Ни CRL, ни срока годности, ни сигнала «ключ мёртв». owfeed делает ротацию
  дешёвой и не утверждает, что отзыв существует.
- **Вашему ключу доверяют для любого имени пакета.** См. [А фид вам вообще нужен?](#а-фид-вам-вообще-нужен).
- **Attended Sysupgrade теряет ваши пакеты.** `owut` не передаёт кастомные репозитории, а
  `repository_allow_list` на сервере ASU по умолчанию пуст и поэтому запрещает всё.
- **`build` пакует каталог и не собирает его.** Соберите CSS заранее. Каталоги `.po` owfeed
  компилирует сам, потому что LuCI молча игнорирует `.po`. Вашу сборку он не запускает и паковать
  исходники отказывается.
- **Сборок через SDK нет и не будет.** Собирайте [owlab](https://github.com/owfeed/owlab),
  `openwrt/gh-action-sdk` или своим вызовом SDK и оставьте результат в `dist/<arch>/`. См.
  [контракт артефакта](docs/artifact-contract.md).

Ещё не реализованы, хотя схема их принимает, чтобы попытка их использовать давала внятную ошибку:
`retention:`, `overrides:`, `build.changed-only`, `version-from: git-describe`, цели публикации `s3`
и `rsync`. Работает только цель `github-pages`. Также нет SBOM, команд ротации ключа и
переиспользования уже опубликованного пакета вместо переподписи.

## Почему не `openwrt/gh-action-sdk`?

Он компилирует, owfeed публикует. Большинству сторонних пакетов нужна только вторая половина.

| | `gh-action-sdk` | `owfeed` |
|---|---|---|
| что делает | собирает пакет из исходников, в SDK | пакует уже собранный каталог |
| noarch на 35 архитектур | 35 сборок SDK | одна, ~25 секунд |
| индекс | — | подписанный, apk и opkg сразу |
| подпись | `PRIVATE_KEY` пишется в `$TOPDIR` | ключ не попадает в сборочный job |
| публикация | — | GitHub Pages, через гейт |
| доказательство, что ставится | — | `smoke`, на живом образе OpenWrt, с провалом, если apk просит `--allow-untrusted` |
| доказательство, что живой фид работает | — | `verify`, по задокументированному URL |
| релизные линии | одна за запуск | apk и opkg из одного конфига, каждая подписана схемой, которую проверяет её менеджер |
| конфиг | входы workflow | `owfeed.yml` с [опубликованной схемой](schema/v1.json), сгенерированной из кода |

Компилируемому C нужен SDK, и owfeed упакует то, что он выдал. Тему LuCI, приложение LuCI, скрипт
или статический бинарь компилировать не нужно.

## Чужой CI, мой фид

Фид с чужими пакетами никогда не отдаёт авторам свой ключ. Авторы собирают и подписывают в своём CI
и публикуют подписанный релиз. Фид забирает его и проверяет подпись автора запиненным ключом.

```sh
owfeed sign                       # в CI автора, ключом автора
owfeed doctor --require-origin    # каждый пакет называет свой репозиторий
```

- По умолчанию фид подписывает и каждый пакет. Блоки подписей apk складываются, поэтому
  установленный файл несёт **обе** подписи.
- С `signing.sign-packages: false` фид подписывает только индекс, откуда роутер и так берёт доверие.
  Установка, обновление и удаление по имени работают так же. Перестают работать `apk add ./file.apk`
  и загрузка пакета через LuCI; обоим и для собственных пакетов OpenWrt уже нужен
  `--allow-untrusted`.

### Если вы автор

У вашего репозитория есть ipk-линия, и индекс он не собирает: индекс подписывает своим ключом фид.
Вы публикуете релиз и подписанную опись того, что в него входит:

```sh
owfeed plan                       # что даст сборка, офлайн
owfeed check                      # на пулл-реквесте: build, sign, index, doctor, одноразовые ключи
owfeed --frozen-lock build
owfeed release --repo "$GITHUB_REPOSITORY" --tag "$GITHUB_REF_NAME"
```

- **`plan`** печатает версию, архитектуры и путь каждого файла, ничего не собирая. У `--json` есть
  версия, поэтому следующий job читает его и не шарит по `dist/`. Раньше всего он отвечает при
  `version-from: tag` (`tag:v` срезает `v`).
- **`check`** создаёт по одноразовому ключу каждого вида и выбрасывает их после запуска. Запускайте
  его на пулл-реквестах: секрет подписи в job, который выполняет код форка, — это секрет, на который
  форк может нацелиться. Блок `signing:` ему не нужен.
- **`release`** пишет `manifest.txt` с размером и хешем каждого файла и подписывает его usign-ключом.
  Роутер проверяет такую подпись, ничего не устанавливая. Манифест несёт имя репозитория, и читатели
  его проверяют: подпись доказывает, кто написал, но не о чём это.
- Ассеты релиза плоские, а в имени apk архитектуры нет. Где имена сталкиваются, `release` дописывает
  архитектуру; noarch-пакет сохраняет имя, по которому его ищут установщики.

[CONTRIBUTING фида](https://github.com/owfeed/owfeed-packages/blob/main/CONTRIBUTING_ru.md) разбирает
обе стороны. Живой фид, собранный так: [owfeed/owfeed-packages](https://github.com/owfeed/owfeed-packages),
тема LuCI и статический Go-бинарь на 20 архитектур. Его пулл-реквесты собирают, подписывают,
индексируют и проверяют всё на одноразовом ключе.
